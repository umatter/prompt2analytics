# Methods registry

`validation/methods/<area>.json` lists the methods whose numbers are pinned to R: which R
reference cases (`validation/expected/<id>.json`, written by `Rscript validation/r/run.R
--write`) a method is checked against, by which tests, for which quantities and at which
tolerance. The status page (`validation/VALIDATION_STATUS.md`, generated by
`validation/tools/validation_status.py render`) lists exactly these methods under
"Methods pinned to R"; every other `test_validate_*` test is reported as not registered.
`validation_status.py lint` checks the registry against the case files, the test lists and
the sources.

Each package owns its own registry file (`regression.json`, `panel.json`, ...), so
packages that work in parallel never edit the same file.

## Schema

A registry file is `{"schema": 1, "methods": [<method>, ...]}`. A method has exactly these
keys:

| Key | Type | Meaning |
|---|---|---|
| `id` | string, `^[a-z0-9_]+$` | Unique over all registry files. |
| `name` | string | Human-readable name of the method. |
| `category` | string | `stats`, `regression`, `econometrics`, `forecasting`, `ml`, `cli`, `mcp`, or `interfaces`: CLI exhibit and MCP pins, `validation/methods/interfaces.json`. |
| `reference` | string | The R function(s) the cases call. |
| `doc` | string | Repository-relative path of the method document; must exist. |
| `cases` | non-empty list of strings | Case ids; each needs `validation/expected/<id>.json`. A case may be listed by several methods. |
| `tests` | non-empty list of strings | Test ids (below) of the tests that load the cases. |
| `quantities` | list of strings | What the tests pin (coefficients, SE types, statistics, ...). |
| `tolerance` | string | The tolerance row of `validation/README.md` used, and why if it is looser. |
| `deviations` | list of objects | Known mismatches with R (below); `[]` if none. |
| `supersedes_legacy` | list of strings | Paths of legacy `validation/expected/*.csv` files whose values these cases replace; each must exist. |

Test ids:

- unit tests (a lib or bin target): `<package>::<libtest path>`, for example
  `p2a-core::econometrics::panel::tests::test_validate_panel_re_grunfeld`;
- integration tests (`tests/<bin>.rs` or `tests/<bin>/main.rs`):
  `<package>::<test binary>::<name>`, for example
  `p2a-core::validation_ml_advanced::test_validate_c50_classification`.

These are the ids `validation_status.py` builds from `cargo test -- --list` output, and the
lint looks each one up in the list of its package.

## Deviations

A deviation is `{"finding": "<ID>", "quantity": "<what>", "note": "<why>"}`, with `finding`
a review finding id (`^[A-Z]+-[0-9]+$`, for example `REG-50`). A method with deviations is
"R-pinned with known deviations": the quantity named is left out of the test's `Check`
(with a `// deviation <ID>` comment at that spot) until the finding is fixed. Never widen a
tolerance to make a mismatch pass; record the deviation instead.

## Example

An example entry (the shape of the panel random-effects pin; not a registered method):

```json
{
  "schema": 1,
  "methods": [
    {
      "id": "panel_re",
      "name": "Random effects (Swamy-Arora GLS)",
      "category": "econometrics",
      "reference": "plm::plm(model = 'random'); plm::ercomp; plm::vcovHC(method = 'arellano')",
      "doc": "validation/econometrics/panel_re.md",
      "cases": ["panel_re_grunfeld", "panel_re_grunfeld_unbalanced"],
      "tests": ["p2a-core::econometrics::panel::tests::test_validate_panel_re_grunfeld"],
      "quantities": ["coefficients", "SE classical", "SE Arellano HC0/HC1", "z", "p", "95% CI", "sigma_e^2", "sigma_u^2", "theta", "R2", "Wald chi2"],
      "tolerance": "validation/README.md, n = 120-300: coefficients 1e-8, SE and statistics 1e-6 relative",
      "deviations": [],
      "supersedes_legacy": ["validation/expected/panel_re_full.csv"]
    }
  ]
}
```

## What the lint checks

`python3 validation/tools/validation_status.py lint [--tests <pkg>-tests.txt ...] [--strict]`
prints one line per finding (`ERROR [rule] <path>[:<line>]: <message>` or `WARNING ...`) and
a summary line. A `--tests` file is the output of `cargo test -p <pkg> --tests -- --list`
and must be named `<pkg>-tests.txt`. Colour codes in it (`CARGO_TERM_COLOR=always`) are
ignored; a file with no cargo `Running <target>` line is a usage error (exit 2), since
every registered test would otherwise look absent.

Always errors (CI gates on these now):

- `registry`: a registry file that does not parse, has another schema, has no `methods`
  list, or a method with a missing, extra or mistyped key, an invalid id, a duplicate id,
  a `category` outside the list above, an invalid deviation or a `supersedes_legacy` path
  that does not exist.
- `case-file`: a registry case without its JSON; a `validation/expected/*.json` that does
  not parse as a schema-1 case (a `{names, values}` value needs as many names as values),
  whose `id` is not its file name, whose `dataset` or `datasets` paths do not exist, or
  whose `dataset` is not in `datasets`; a test that loads a case id that has no file.
- `orphan-case`: a schema-1 case that no method lists (cases of area `harness` are exempt).
- `unknown-test`: a registry test id that is not in its package's `--tests` list (packages
  without a list are named in a `note:` line instead).
- `unregistered-load`: a `fn test_*` in `crates/*/src` or `crates/*/tests` that calls
  `Case::load("<id>")`, `Case::try_load("<id>")` or `load_case("<id>")` while no method
  lists that case together with a test of the crate's package of that name.
- `registered-test-loads-no-case`: a registry test whose package and name match a scanned
  `fn test_*` (by its last path segment, as `unregistered-load` does) whose body neither
  loads one of the method's cases with one of the three calls above nor names one in a
  string literal. The literal counts because a test may load its case through a helper,
  `grunfeld_case("panel_re_grunfeld")`; comments do not count. A registry test that
  matches no scanned function is not checked here; `unknown-test` checks that it exists.
- `missing-doc`: a registry `doc` that does not exist.

Warnings, errors with `--strict` (legacy documentation debt; CI switches to `--strict` once
it is cleared):

- `csv-citation`: a comment in a test that loads no case and says it takes its "reference
  values" from a `validation/expected/*.csv` file.
- `dead-link`: a relative Markdown link in `validation/**/*.md` whose target does not exist.
- `dead-test-name`: a test name in `validation/**/*.md`, `README.md` or `CLAUDE.md` (in
  inline code, or in a fenced `cargo test` command, `fn` line or `::` path) that matches no
  test, neither exactly nor as a prefix (a libtest filter matches every test whose path
  contains it; the lint counts a name as live when it equals, or is a prefix of, the last
  path segment of a listed test or of a `fn test_*` in `crates/`). Identifiers that only
  look like test names go into `validation/tools/lint_ignore_names.txt`.
- `missing-dataset`: a `**File**:` entry in `validation/datasets/README.md` with no file.

`validation/reports/` (run output) and `validation/tools/tests/fixtures/` (the lint's own
fixtures) are never scanned.

## Running it locally

```bash
cargo test -p p2a-core --tests --no-default-features --features ci -- --list > target/p2a-core-tests.txt 2>&1
python3 validation/tools/validation_status.py lint --tests target/p2a-core-tests.txt
```

`validation/run_validation.sh` runs the lint with the lists of p2a-core, p2a-cli and
p2a-mcp on every full run (no `--category`).
